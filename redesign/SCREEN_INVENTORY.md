# CycleCare redesign — screen and state inventory

This inventory prevents an attractive feature landing page from hiding missing nested flows. “Existing” below means code is present in the inspected Flutter source; it does not certify that every runtime service is configured. The browser gallery and exported screenshots are design prototypes, not the Flutter implementation.

The original gallery contained these 21 named screen functions: `home`, `calendar`, `log`, `insights`, `pet`, `welcome`, `goals`, `setup`, `companions`, `learn`, `health`, `pregnancy`, `birthcontrol`, `partner`, `reminders`, `settings`, `lock`, `empty`, `success`, `late`, `ai`. Further designed views added during refinement should be matched to the requirements below. A requirement remains open until an actual designed state or a documented shared component covers it; a placeholder toast is not the completed page.

## Current refinement coverage

The refinement now includes **62 actual screen designs and 124 light/dark PNG exports**. See [CURRENT_COVERAGE.md](CURRENT_COVERAGE.md) for the authoritative file-by-file index. The “Original gallery coverage” column below records the initial audit; the added detail/settings/onboarding/recovery designs now cover those named gaps. Production bindings, all runtime state variants and data/service work still follow the implementation plan. Reusable reading, condition, form and recovery patterns apply to their corresponding variants.

## New or expanded feature states

The expanded logging catalogue intentionally includes product ideas beyond `DailyLog`. Their design presence does not mean they are implemented. The catalogue must identify every addition's status and source evidence. Examples requiring separate implementation if present in the catalogue include multiple moods, structured intimacy/protection/libido records, exercise type/duration, expanded appetite/digestion details, reproductive test results and repeatable medication entries.

Do not use the inactive `AppConstants` lists to mark extra options as implemented. The inspected active tracking options contain 16 built-in symptoms and 10 moods; legacy aliases and stored custom tags must remain readable after migration.

## Reference capture requirements

Actual installed-app captures belong in a clearly separate My Calendar research folder. Record package identifier, app version when obtainable, Android version/device, capture date, screen/flow name and whether the state was genuinely visited. Record transitions as video, since PNGs cannot demonstrate motion.

Capture onboarding from first launch if accessible without destroying unrelated data, then visit all reachable pages including reminders, logging category expansions, settings and nested forms. Paywalls, unavailable features, sign-in requirements, permissions, empty-data-dependent states and installation failures must be recorded honestly as coverage limitations. Do not label store promotional images or a recreated animation as installed-app evidence. Do not purchase a subscription, invent account access or bypass access controls to fill a checklist.

## Completion rule

The word “all” means each applicable route, nested view/form and meaningful state in this inventory has a design or a documented reusable design pattern. Mark implementation separately from design. Keep [IMPLEMENTATION_PLAN.md](IMPLEMENTATION_PLAN.md) and this inventory current as new views are added; all future additions must match the same approved CycleCare UI, icon family and fluid/reduced-motion behavior.
